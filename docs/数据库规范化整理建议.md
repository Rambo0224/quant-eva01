# Quant 工程数据库规范化整理建议

## 1. 文档目的

本建议面向工程的通用数据底座。数据库应服务于行情查询、宏观数据、研究分析、图表和后续应用，基础表不应为某一个指标、策略或页面定制字段。

本文只提出数据库结构、数据治理和整理顺序，不规定任何具体分析功能。

## 2. 当前数据库观察

当前主库为 `data/replay.duckdb`，已有行情、ETF 份额、宏观观测值、原始载荷、数据源和图表登记等表。主要问题不是缺少数据表，而是不同数据域的命名和规范尚未完全统一：

- `equity_daily_bars` 使用 `obs_time`，而日线数据更适合使用明确的 `trade_date`。
- 同一行情表中混有纯代码、带交易所后缀代码和不同来源的同一标的。
- 股票、ETF 和其他资产的身份信息没有统一的标的主数据表。
- 数据源、原始数据、清洗后数据和应用产物尚未通过清晰的分层边界区分。
- `extra` JSON 适合保存原始扩展信息，但不应代替核心字段。
- `sources` 当前没有完整登记内容，数据源引用存在但数据源元数据不足。
- `amount`、`turnover_rate` 等字段部分为空，字段单位和缺失语义需要明确。

## 3. 推荐的数据分层

建议采用三层结构：

```text
raw      原始接入层：保留供应商返回内容和原始字段
core     标准核心层：统一实体、日期、单位、代码和数据口径
mart     应用数据层：面向报表、图表、查询或具体产品的派生结果
```

核心层是整个工程的公共接口。任何功能都读取 `core` 层，不能直接依赖某个供应商表或 `raw` 层字段。应用层可以重建，不能反向修改核心行情数据。

## 4. 标的主数据

建立统一的 `instrument_master`，每个证券或金融资产只对应一个内部稳定标识。建议字段：

```text
instrument_id       内部唯一 ID
symbol              规范代码，例如 600000.SH、510300.SH
name                当前名称
asset_type          stock / etf / index / future / bond 等
exchange            SH / SZ / BJ 等
currency            计价币种
list_date
delist_date
status              active / delisted / suspended 等
created_at
updated_at
```

另外建立 `instrument_identifiers`，保存供应商代码、旧代码、证券简称和代码生效区间。这样可以解决 `000001` 与 `000001.SZ`、不同供应商代码之间的映射问题，同时保留历史变更。

## 5. 统一时间和行情表

标准行情表建议命名为 `market_daily_bars`，不要继续使用只适用于股票的 `equity_daily_bars`。建议字段：

```text
instrument_id
trade_date          DATE
frequency           1d
open
high
low
close
volume
amount
turnover_rate
open_interest       可为空，适用于有该字段的资产
price_adjustment    raw / qfq / hfq / total_return 等
currency
volume_unit
amount_unit
source_id
ingested_at
```

日线使用 `trade_date`；分钟或其他频率另行使用 `bar_time` 或独立频率表，避免把日期和时间混在同一字段中。价格口径、成交量单位和成交额单位必须随数据保存，不能依赖程序员记忆。

同一价格口径下建议设置唯一键：

```text
(instrument_id, trade_date, frequency, price_adjustment)
```

不同供应商的原始记录留在 `raw` 层，标准核心层只保留按优先级选定的一条有效记录，并记录 `source_id`。

## 6. ETF 份额和规模数据

ETF 份额、份额变化、规模和估算资金流与行情属于不同事实主题，建议保留为独立的 `etf_daily_facts`，通过 `instrument_id + trade_date` 关联标的主表和行情表。不要把份额字段塞入通用行情表，也不要把 ETF 份额表当作 ETF 行情表。

## 7. 数据源和采集记录

完善 `sources` 表，至少登记：

```text
source_id
provider
source_type
endpoint_or_method
license_note
priority
coverage
enabled
meta
```

建议增加 `ingestion_runs` 和 `ingestion_errors`，记录每次采集的开始时间、结束时间、请求范围、读取行数、写入行数、覆盖日期、状态和错误信息。`raw_payloads` 继续保留请求和原始响应，便于审计和重放。

## 8. 数据质量和约束

标准层入库前应检查：代码是否能映射到主数据、日期是否有效、主键是否重复、OHLC 是否为空、`high >= max(open, close, low)`、`low <= min(open, close, high)`、价格和数量是否为非负值、单位是否明确、是否出现异常日期缺口。缺失值统一使用 `NULL`，不要用 0 表示未知。

建立 `data_quality_results`，按数据批次和标的记录检查项、异常数量、严重程度、处理状态和说明。质量问题应可追踪，不应在清洗时静默丢弃。

## 9. 字段和类型规范

- 主键、外键和代码字段使用稳定的字符串或整数 ID，避免用名称作为关联键。
- 日期使用 `DATE`，采集时间使用带时区语义的时间戳或统一 UTC 时间。
- 金额、价格、数量使用明确的数值类型；不把数字存为字符串。
- JSON 只存供应商原始扩展字段，不存核心查询条件。
- 表名、字段名统一使用英文蛇形命名；中文名称放在元数据或字典中。
- 所有枚举值建立数据字典，避免同一含义出现多种拼写。

## 10. 整理实施顺序

1. 先盘点现有表、来源、代码格式、日期范围和重复记录。
2. 建立 `instrument_master` 与代码映射表。
3. 完善 `sources`，登记现有来源和优先级。
4. 保留现有表作为原始层，新增标准核心表，不直接破坏原表。
5. 将股票和 ETF 日线数据清洗、统一代码、统一日期、去重后写入核心行情表。
6. 将 ETF 份额数据独立归入 ETF 事实表。
7. 增加质量检查、采集批次和错误记录。
8. 将现有查询、图表和应用逐步切换到核心层。
9. 连续运行一段时间并核对行数、日期范围、标的数量和抽样价格后，再考虑归档旧结构。

## 11. 验收标准

整理完成后，应能回答：一个标的是什么、来自哪些代码体系、属于哪类资产、哪天有哪种口径的行情、数据来自哪个来源、何时采集、是否通过质量检查。任何应用功能都应只依赖这些稳定的公共字段，而不依赖某个数据源的特殊命名或 JSON 内部结构。
